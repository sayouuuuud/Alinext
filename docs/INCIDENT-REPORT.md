# تقرير تشخيص وإصلاح ربط AliFleet مع WordPress وWooCommerce

## 1. نطاق التقرير

يوثق هذا الملف المشكلة التي بدأت بها المحادثة، الفحوص التي نُفذت، الإصلاحات التي أُجريت، نتائج الاختبارات، الحالة الحالية، وما تبقى معلّقًا.

> ملاحظة أمنية: لن يتضمن التقرير كلمات مرور، مفاتيح SSH خاصة، رموز جلسات، cookies، أسرار بيئة، بيانات عملاء، أو محتوى ذاكرة/سياق داخلي غير مخصص للمشاركة. تم استخدام بيانات الاتصال فقط لتنفيذ الفحوص، ولم تُحفظ الأسرار في المستودع أو هذا الملف.

## 2. المشكلة الأصلية

كانت واجهة AliFleet الأمامية مرتبطة بمتجر WordPress/WooCommerce على `a-f.site`. عند محاولة استخدام السلة والانتقال إلى checkout، كانت الرحلة تنتهي بصفحة 404 أو بتحويل غير صحيح إلى تسجيل الدخول في WordPress.

الأعراض التي ظهرت أثناء التشخيص:

- `/checkout/` يعيد 404 عند عدم نشر صفحة الدفع.
- WooCommerce كان يملك تعيينًا لصفحة checkout برقم `938`، لكن الصفحة كانت `draft`.
- نقل السلة كان ينشئ جلسة WooCommerce ثم يحوّل إلى `?page_id=938`، والصفحة غير المنشورة كانت تمنع إكمال الدفع.
- بعض طلبات Preview كانت تُحوّل إلى تسجيل الدخول لأن origin المعاينة لم يكن ضمن قائمة origins المسموح بها في إضافة WordPress.
- GraphQL كان يعيد `null` لصفحات CMS المطلوبة، بينما كانت الواجهة تعرض fallback أو بيانات ثابتة/احتياطية في بعض المسارات.
- اتضح أن المشكلة لم تكن في المنتجات نفسها: المنتجات والمقالات كانت منشورة، بينما صفحات WordPress الأساسية كانت مخفية بحالة `draft`.

## 3. الوصول الآمن

تم تجهيز وصول SSH مؤقت للحساب المخصص للفحص، مع:

- مفتاح SSH مؤقت بدل إدخال كلمة المرور في أوامر متكررة.
- صلاحيات محدودة على `wp-agent` فقط.
- عدم منح وصول عام إلى Docker أو كامل السيرفر.
- استخدام `sudoers` مقيد للأوامر اللازمة لفحص وإدارة WordPress.
- توقّف الوصول لاحقًا بسبب انتهاء صلاحية المفتاح المؤقت. هذه هي المشكلة الحالية التي أوقفت آخر خطوة رفع، وليست مشكلة في كود checkout نفسه.

بعد انتهاء صلاحية المفتاح، لم يتم الادعاء بأن آخر تعديل وصل إلى الإنتاج، ولم تتم إعادة المحاولة باستخدام وسائل غير آمنة.

## 4. خطوات التشخيص التي نُفذت

### 4.1 فحص المشروع المحلي

تمت مراجعة بنية مشروع Next.js والملفات المتعلقة بـ:

- مسار checkout: `app/checkout/[[...path]]/route.ts`
- مسار WooCommerce AJAX: `app/wc-ajax/route.ts`
- مسار CMS: `app/cms/[[...path]]/route.ts`
- بروكسي checkout: `lib/checkout/proxy.ts`
- إجراءات السلة والتحويل: `lib/checkout/actions.ts`
- بوابة الحماية: `lib/checkout/gate.ts`
- إعدادات WordPress: `lib/wp/config.ts`, `lib/wp/client.ts`, `lib/wp/settings.ts`
- استعلامات المحتوى والسياسات والسيارات والكتالوج
- إضافة WordPress الرئيسية: `wordpress/mu-plugin/alifleet-cms.php`
- إضافة التحويل: `wordpress/mu-plugin/alifleet-headless-redirect.php`
- فحوص السيرفر: `wordpress/server/agent-preflight.sh`
- أداة الاستعادة: `wordpress/scripts/repair-required-pages.php`
- إعدادات Next.js وheaders

كما تم فحص lockfile وscripts المتاحة، وتشغيل TypeScript والبناء الإنتاجي.

### 4.2 فحص WordPress وWooCommerce

تم فحص:

- وجود `wp-agent` والصلاحيات المقيدة.
- حالة إضافات WordPress.
- إعدادات WooCommerce الخاصة بصفحات المتجر والسلة والدفع والحساب.
- حالة الصفحات ومطابقة ID/slug/type.
- GraphQL وREST والروابط العامة.
- الإضافات المفعلة وأدوات النسخ الاحتياطي.
- الملفات المنشورة فعليًا في `mu-plugins` ومقارنتها بنسخ المستودع.
- بنية الروابط الدائمة، والتي كانت `/%postname%/`.

## 8. الإصلاحات التي نُفذت فعليًا

### 8.1 نشر صفحات WooCommerce

تم نشر صفحات WooCommerce الأربع: shop، cart، checkout، my-account.

### 8.2 نشر صفحات CMS والسياسات

تم نشر الصفحات الـ15 الأخرى ضمن القائمة المعتمدة، فأصبح مجموع الصفحات المنشورة 19 صفحة.

تمت مقارنة العناوين والمحتوى والبصمات قبل وبعد، وكانت النتيجة أن التغيير اقتصر على حالة النشر ولم يتغير محتوى الصفحات أو الـIDs.

### 8.3 مزامنة إضافات WordPress

تم تحديث/رفع التعديلات المتعلقة بـ:

### 8.4 حماية التحويل

تم الحفاظ على حماية WordPress العامة، مع استثناءات محددة لمسارات checkout/cart والبروكسي اللازمين للفرونت إند.

تم تضييق التحقق بحيث:

- لا يكفي header مزور وحده للوصول إلى صفحات الإدارة.
- لا يوجد bypass عام لكل صفحات WordPress.
- مسارات الدفع وWooCommerce AJAX فقط تحصل على الاستثناء المطلوب.
- GraphQL وREST والطلبات اللازمة للمحتوى تعمل دون فتح لوحة الإدارة.

### 8.5 إبطال الكاش والتحذيرات

تم تعديل منطق CMS بحيث:

- لا يتكرر إبطال الكاش عند كل نشر بلا داعٍ.
- يتم التعامل مع الانتقال من publish إلى draft/private/trash.
- autosaves وrevisions لا تسبب invalidation غير ضروري.
- توجد تحذيرات عند غياب أو عدم نشر صفحات WooCommerce الأساسية.
- تم توسيع فحص preflight ليرصد تعطل checkout بدل اعتباره نجاحًا.

### 8.6 حماية كاش checkout

تم تعديل بروكسي checkout وheaders Next.js بحيث تكون ردود checkout وWooCommerce AJAX:

- `Cache-Control: private, no-store`
- بدون `ETag` أو `Last-Modified` حيث يلزم
- غير قابلة للتخزين العام

كما تمت إضافة headers صريحة للمسارات الحساسة حتى تشمل redirects/errors التي يصدرها Next.js قبل وصولها للبروكسي.

## 9. المشاكل التي ظهرت وكيف تم حلها

### المشكلة 1: checkout 404

**السبب:** صفحة checkout رقم 938 كانت `draft`.

**الحل:** نشر صفحة checkout بعد مطابقة ID/slug/content، ثم اختبارها بجلسة WooCommerce.

### المشكلة 2: صفحات CMS لا تظهر من GraphQL

**السبب:** الصفحات الأساسية كانت `draft`، لذلك GraphQL العام أعاد `null`.

**الحل:** نشر الصفحات الـ19 المعتمدة فقط، ثم إعادة اختبار GraphQL والبصمات.

### المشكلة 3: لا يمكن استخدام نسخة repo القديمة من redirect كما هي

**السبب:** النسخة المنشورة على السيرفر كانت تحتوي استثناءات دفع مهمة غير موجودة في نسخة قديمة من المستودع.

**الحل:** مقارنة النسختين ودمج الاستثناءات الصحيحة بدل استبدال الملف عشوائيًا.

### المشكلة 4: Preview origin غير مسموح

**السبب:** نطاق المعاينة الفعلي `https://sb-6h9l3x6zv41u.vercel.run` لم يكن ضمن origins المسموحة في WordPress.

**الحل المحلي:** تعديل قائمة origins في البروكسي/التحقق ليشمل نطاق المعاينة الحالي دون توسيع السماح لمسارات أخرى.

**الحالة:** يحتاج هذا التعديل إلى رفع نهائي للسيرفر وإعادة اختبار checkout من المتصفح؛ هذه آخر نقطة متوقفة بسبب SSH.

### المشكلة 5: اختبار GraphQL باسم حقل غير صحيح

**السبب:** أحد الاختبارات استخدم حقلًا تجريبيًا غير موجود في schema (`productsFeed`).

**الحل:** إعادة الاختبار بأسماء WooGraphQL الصحيحة؛ الاختبار المباشر الصحيح نجح.

### المشكلة 6: اختبار checkout بدون سلة

**السبب:** checkout الفارغ يرجع للسلة حسب سلوك WooCommerce المتوقع.

**الحل:** إعادة الاختبار بنفس جلسة cookies وبعد نقل منتج فعلي، ونجح checkout بـHTTP 200.

### المشكلة 7: اختبار handoff من جلسات مختلفة

**السبب:** اختبار نقل السلة الأول فصل بين جلسة إنشاء السلة وجلسة فتح checkout، فظهرت نتيجة redirect مضللة.

**الحل:** استخدام cookie jar واحد وتتبع التحويلات بنفس الجلسة.

### المشكلة 8: PHP غير متوفر محليًا

**السبب:** VM المحلي لا يحتوي مفسر PHP.

**الحل:** تشغيل فحص PHP داخل كونتينر/بيئة WordPress عبر `wp-agent`.

### المشكلة 9: lint غير متاح

**السبب:** يوجد script لـESLint لكن حزمة `eslint` غير موجودة ضمن dependencies الحالية.

**الحل:** عدم إدخال dependency جديدة خارج نطاق الإصلاح؛ تم الاعتماد على TypeScript/build وفحوصات Bash/PHP المتاحة.

### المشكلة 10: SSH انتهت صلاحيته

**السبب:** المفتاح المؤقت انتهت مدته، ومحاولة المفتاح الجديد لم تنجح لأن المفتاح لم يكن مثبتًا على السيرفر.

**الحل المتاح:** تثبيت مفتاح مؤقت جديد عبر حساب لديه sudo باستخدام أمر محدود، ثم إعادة رفع تعديل Preview origin واختبارات القبول.

**الحالة الحالية:** لم يتم الادعاء بنجاح الرفع الأخير؛ الإنتاج لم ��ُعتبر مكتمل الإصلاح من ناحية Preview origin حتى إعادة الاتصال.

## 14. سياسة الرجوع

- الرجوع يكون للملف أو الصفحة المتأثرة فقط.
- لا تُستعاد قاعدة البيانات كاملة على متجر حي كحل أول، حتى لا تضيع طلبات جديدة.
- لا تُعاد صفحة checkout إلى draft إلا مع فهم أن ذلك يعيد 404.
- أي رجوع للصفحات يتحقق من عدم وجود تعديل أحدث عليها.
- بعد الرجوع يجب تحديث الكاش وإعادة اختبارات الصحة.

## 15. معلومات لم يتم تضمينها لأسباب أمنية

طلب المستخدم تضمين كل بيانات cache memory بلا استثناء. لا يمكن تضمين أو تصدير:

- كلمات المرور.
- مفاتيح SSH الخاصة أو العامة إذا كانت حساسة للسياق.
- cookies وsession tokens وJWTs.
- أسرار البيئة وWebhook secrets.
